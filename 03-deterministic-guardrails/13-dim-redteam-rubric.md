# 13 维红队系统与代码评审框架（Red-Team Review Rubric）

> 面向 AI 协同生成代码与复杂工作流评审的标准化验收记分表。核心铁律：**「能跑只是最低门槛；先抬头看系统级与模块级，再低头看行级；13 维逐项强制表态，禁止选择性跳过。」**

---

## 一、三层评审顺序（严禁倒置）

1. **系统级（System）**：这次改动让系统整体变好还是变坏？引入了什么新耦合？失败会波及哪些上游/下游？
2. **模块级（Module）**：这段逻辑该长在这个模块里吗？与邻居模块的职责边界清不清楚？
3. **行级（Line）**：具体哪一行（`file:line`）在什么输入或时序下会炸？

---

## 二、13 维强制表态检查表

| # | 评审维度 | 核心拷问 |
| :-: | :--- | :--- |
| 1 | **正确性** | 计算对吗？状态机闭合吗？所有分支返回值都合法吗？ |
| 2 | **失败路径** | IO / 网络 / 解析 / 外部依赖失败时谁接住？是否存在空 `catch` 静默吞错或误报成功？ |
| 3 | **边界与状态** | 空集、单元素、重复键、0/负数/极值、超长串、畸形 JSON、编码与大小写空白。 |
| 4 | **数据契约** | 边界入参校验了吗？异常路径上的出参是否仍满足调用方契约？ |
| 5 | **并发与生命周期** | 重入、竞态、锁粒度、幂等性、顺序依赖；句柄/连接/监听器在异常路径会漏关吗？ |
| 6 | **性能与复杂度** | 循环里藏了 $O(n^2)$ 或重复 IO 吗？有无无界增长的内存/缓存？热路径有无同步阻塞？ |
| 7 | **安全** | 不可信输入是否直达路径/命令/DOM/模板？密钥是否进日志、URL 或仓库？ |
| 8 | **可测试性** | 隐藏全局状态、时间、随机源是否阻断单测？靠过度 Mock 撑着的测试是否等于没测？ |
| 9 | **可观测性** | 出故障时日志是否带足上下文（ID、参数、上游节点），还是只留一句“操作失败”？ |
| 10 | **结构与分层** | 是否单函数分支过多/嵌套过深/职责混杂？抽象是过度还是不足？ |
| 11 | **重复实现** | 同类逻辑在全仓库出现几次？是否无故手写标准库已有能力？ |
| 12 | **可维护性** | 改一个需求要动几处无关文件？魔法数字/字符串是否散落？错误包装是否吞掉原始堆栈？ |
| 13 | **写法取舍** | 针对关键结构决策强制分类：**「严格更好」**（少状态/少失败模式，必改） / **「各有取舍」**（标明切换条件） / **「现写法确实更好」**（放过，绝不硬编争议）。 |
